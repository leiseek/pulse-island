# Pulse Island · Design Package Review Ledger

**Review date:** 2026-07-01  
**Scope:** `README.md` and the current numbered design series `00` through `24`  
**Review mode:** Per-document closure review plus cross-document consistency audit  
**Status:** Historical closure review. Its P0 items were converted into `25-consistency-closure.md`, gate audits, and implementation tests. Do not use this file to reopen W0/W1/W2/W3 or delay current W4 work.

---

## 1. Executive verdict

Pulse Island has a strong and unusually coherent core:

- Observe-first is consistently safer than “control first.”
- The state model, event reducer, privacy boundary, Drop Mode, and provider probe model reinforce one another.
- The package correctly rejects transcript scraping, UI automation, private protocol emulation, PATH hijacking, and fabricated task certainty.
- The design is implementation-shaped: it has modules, fixtures, performance limits, failure handling, and user-visible truthfulness rules.

The package is **not** ready to be treated as a single normative specification yet. Eight cross-document closure issues could lead different implementation agents to build incompatible behavior. None require a redesign. They require one explicit source of truth per topic and a small set of wording/fixture corrections.

### Overall readiness by layer

| Layer | Review result | Notes |
|---|---|---|
| Product posture and privacy | Strong, with two wording conflicts | The core promise is sound. Provider scope and safe-title rules need correction. |
| State / reducer / arbitration | Strong foundation, one P0 logic conflict | The limited-vs-waiting priority must be encoded exactly. |
| Link / Drop Mode / transport | Strongest subsystem | Spike C should become the single runtime/IPC authority. |
| Context routing / Windows observation | Strong, one label-strength inconsistency | Exact and strong routes need distinct user wording. |
| Provider capability posture | Probe cards are strong | Older overview documents overpromise compared with current probe cards. |
| Native UI | Strong | It needs to inherit the corrected routing/provider/fuel vocabulary. |
| Implementation roadmap | Directionally sound, not yet canonical | Gate, spike, and work-package order need one dependency staircase. |
| Reliability / install / onboarding | Strong | Safe Mode and Strict retention precedence need an executable contract. |

## 2. P0 closure items

These are the changes that should be made before implementation decisions can rely on the package without a human interpreting conflicts.

### R-01 · Provider support envelope is overclaimed in the product overview

**Severity:** P0  
**Documents:** `00-product-foundation.md`, `07-adapter-ecosystem.md`, `19-antigravity-probe-card.md`, `20-onboarding-settings-and-capability-disclosure.md`, `README.md`

`00` calls Codex CLI, Claude Code, and Antigravity CLI “P0 surfaces” and describes a shared P0 promise including red/yellow/green/off, safe summary, completion/error visibility, and return to context. `19` correctly says Antigravity has no established formal integration and starts at Passive / Observed only. `20` also presents Antigravity as process-observed only.

This is a release-claim conflict, not merely a wording issue. An implementer could interpret `00` as permission to render Antigravity as active, completed, or failed based on process presence.

**Decision to lock:**

```text
MVP supported_observe provider = one provider selected after W4 probe race.
Codex CLI and Claude Code = probe candidates, not blanket P0 support claims.
Antigravity = Passive / Observed only unless its probe independently raises a capability.
```

**Required edits:**

1. Replace “P0 surfaces” in `00` with “Provider candidates and current capability ceilings.”
2. Add a small product-wide provider matrix whose entries are sourced from the Provider Probe Cards.
3. State explicitly that a provider may appear in the product while only supporting Passive / Observed mode.
4. Update `README.md` to say the first supported Observe adapter is chosen after the Codex/Claude probe race; Antigravity remains probe-gated.

**Acceptance fixture:** A process-only Antigravity candidate cannot render green, yellow, red, completed, failed, task title, or Fuel.

### R-02 · Fuel posture conflicts with the current provider evidence

**Severity:** P0  
**Documents:** `00-product-foundation.md`, `07-adapter-ecosystem.md`, `10-verification-gates-and-mvp-roadmap.md`, `16-codex-cli-probe-card.md`, `17-claude-code-probe-card.md`, `20-onboarding-settings-and-capability-disclosure.md`

`16` says Codex task-token ledger is unavailable until a formal task-scoped source exists. Its account rate-limit read is an experimental, independently scoped App Server probe. `17` says Claude account quota and current-session token totals are unavailable in P0, with only a narrow P1 subagent numeric probe possible.

Older overview documents still describe Codex local task ledger / full Fuel and Claude session Fuel as P0 targets. That violates the product’s own “source-gated, no fabricated usage” principle.

**Decision to lock:**

```text
P0 Fuel baseline for every provider = Unavailable unless a provider-specific probe
has raised a specific capability.

Reported quota, task token ledger, and burn meter are three separate capabilities.
They never become available as a bundle merely because a provider is observed.
```

**Required edits:**

1. In `00`, replace the current provider policy table with capability-by-capability ceilings from `16`, `17`, and `19`.
2. In `07`, remove “session tokens” as a Codex P0 target and “local session token ledger” as a Claude P0 target.
3. In `10`, move session ledger and Burn Meter to a source-gated W6/Fuel enhancement, not a Gate D/E default deliverable.
4. In `20`, show `Usage unavailable` as the normal initial state, not as a provider failure.

**Acceptance fixtures:**

- Codex Hook-only task: no current-task token count.
- Claude Hook-only task: no current-session token count and no quota percentage.
- A verified Codex rate-limit window may display as `Reported` without implying task tokens.
- No Fuel Thread is eligible without a verified scoped source.

### R-03 · Arbitration does not preserve the declared limited-vs-waiting order

**Severity:** P0  
**Documents:** `00-product-foundation.md`, `04-multi-agent-arbitration.md`, `13-spike-b-state-kernel.md`, `24-implementation-work-packages.md`

The product priority in `00` is:

```text
1. Failed / hard blocked
2. Waiting for user
3. Usage limit reached
4. User-pinned task
5. High-confidence fuel risk
6. Resource-caused stall
7. Running
8. Recently completed
9. Idle
```

`04` collapses `failed`, `limited`, and hard external blocks into one `hard_block` class, putting a quota-limited task above a validated waiting-user task. This changes visible behavior and contradicts the declared order.

**Decision to lock:**

```text
failed_or_nonquota_hard_block
> waiting_user
> verified_limit_reached
> user_pinned
> high_confidence_fuel_risk
> resource_caused_stall
> running
> recent_terminal
> idle_or_observed
```

`limited` is not a synonym for generic hard block in presentation arbitration.

**Required edits:**

1. Replace the broad `hard_block` class in `04` with distinct `failed_or_nonquota_hard_block` and `limit_reached` classes.
2. Keep the exact order above as a lexicographic tier order. Do not use hidden weights to reverse it.
3. Update `04` notification examples and primary hold rules accordingly.
4. Add the missing exact fixture to `13` and W1 acceptance in `24`.

**Required fixture:**

```text
failed + waiting_user + limited + running
→ primary = failed

waiting_user + limited + running
→ primary = waiting_user

limited + pinned running
→ primary = limited
```

### R-04 · Exact route labels and strong route labels are currently mixed

**Severity:** P0  
**Documents:** `02-agent-state-model.md`, `05-context-routing.md`, `09-native-island-ui-system.md`, `16-codex-cli-probe-card.md`, `17-claude-code-probe-card.md`, `23-windows-observation-and-window-binding.md`

`23` correctly distinguishes:

- **Exact:** documented provider session route or verified exact target, label `Open original task`.
- **Strong:** validated process-owned relevant window, label `Focus agent window`.

`05` says the phrase `Open original task` is allowed for “Exact or Strong” routes. That makes a strong window correlation sound like a proven original task route. The provider cards correctly aim for workspace-first in P0 and must not inherit this stronger wording.

**Decision to lock:**

```text
Exact       → Open original task / Open provider thread / Focus terminal tab
Strong      → Focus agent window / Focus related terminal
Useful      → Open workspace / Reveal project folder / Open official usage
Weak        → Show process details
```

**Required edits:**

1. Change `05` so `Open original task` is Exact-only.
2. Keep `context_ready` as an internal capability state, but make the label derive from route strength, not context state alone.
3. Ensure `09` renders only Context Router-supplied labels.
4. Update `02` and the provider cards to state that terminal-tab exactness requires host-specific proof, not merely process-window correlation.

**Acceptance fixture:** A verified provider process with one relevant window but no stable tab/session binding must render `Focus agent window`, never `Open original task`.

### R-05 · Link / IPC architecture has two competing authorities

**Severity:** P0  
**Documents:** `06-pulse-link-runtime-architecture.md`, `08-integration-hook-protocol.md`, `14-spike-c-link-transport-drop-mode.md`, `11-rust-workspace-architecture.md`, `24-implementation-work-packages.md`

`14` contains the mature executable contract:

- no long-lived `Idle` Link state
- distinct ingress and Island pipes
- inherited anonymous pipe for first event handoff
- no event on command line
- no raw replay
- full snapshot plus delta protocol
- 90-second grace exit
- precise memory and message caps

`06` still describes an older abstract topology with `Idle → Warm → Active → Drop Mode → Exit`, a single pipe, `EventBatch` bootstrapping, and idle timers. This can cause contradictory implementation work.

**Decision to lock:** `14` is the normative runtime/transport contract. `06` becomes a concise architecture overview that references `14` for lifecycle, pipe topology, startup, timing, and Drop Mode details.

**Required edits:**

1. Remove long-lived `Idle` as a Link process state from `06`; no-work means exit.
2. Replace the single-pipe description with the ingress / Island pipe split from `14`.
3. Remove `EventBatch` from the Island-facing protocol. Island receives only `FullSnapshot`, `SnapshotDelta`, and bounded health/protocol messages.
4. Align `08` wake-up language with inherited first-event handoff from `14`.
5. Make `11` and `24` reference `14` as the concrete protocol source.

**Acceptance fixture:** An Island reconnect can recover with `FullSnapshot` and deltas only. It cannot request or receive raw/normalized Hook event replay.

### R-06 · The execution sequence has multiple incompatible “first” orders

**Severity:** P0  
**Documents:** `README.md`, `10-verification-gates-and-mvp-roadmap.md`, `11-rust-workspace-architecture.md`, `18-first-adapter-selection-and-bootstrap.md`, `24-implementation-work-packages.md`

The package currently contains several valid-but-different orders:

- `10`: Gate 0 includes both Native shell and Link skeleton before A/B.
- `11`: domain/protocol → reducer/routing/arbitration → Win32/UI → Link.
- `18`: Domain/Protocol → Spike B → Spike A → Spike C, while noting A/B can parallelize.
- `24` and README: W0 → W1 → W2 → W3 → W4 → W5 → W6.

The difference matters because implementation agents need to know whether a Link skeleton is expected before the State Kernel, and whether UI can start before W1 has stabilized core types.

**Decision to lock:** `24` is the canonical work-order source. The immediate order is:

```text
W0 Workspace Foundation
→ W1 State Truth Kernel
→ W2 Native Signal Shell
→ W3 Link / Shim / Drop Mode
→ W4 Provider Probe Harness
→ W5 First supported Observe adapter
→ W6 independent context / Fuel enhancements
```

W2 may begin once W0 types and the `PresentationPlan` seam are stable, but W3 cannot begin until W1 passes. That is controlled parallelism, not a separate roadmap.

**Required edits:**

1. Make `10` Gate 0 only the W0 workspace/instrumentation baseline. Move Link skeleton requirements to Gate C/W3.
2. Update `18` to call W1-first the normative path and describe W2 parallel work as optional after W0 contracts stabilize.
3. Add a direct “canonical sequence: see `24`” note to README, `10`, and `11`.

### R-07 · Strict privacy retention needs an explicit precedence rule

**Severity:** P0  
**Documents:** `01-privacy-data-boundaries.md`, `03-event-reduction-engine.md`, `14-spike-c-link-transport-drop-mode.md`, `20-onboarding-settings-and-capability-disclosure.md`, `22-reliability-recovery-and-diagnostics.md`

Default retention is described as an active breadcrumb plus post-terminal safety window, recent terminal tasks, and a bounded recent signal list. `20` defines Strict local state as clearing a task breadcrumb when the task ends and removing post-session history.

The intended behavior is sound, but it is not formally stated which rule wins when terminal checkpointing, grace exit, and Strict mode collide.

**Decision to lock:**

```text
Privacy profile is a retention ceiling.
Strict overrides default recent-terminal retention and default recent-signal retention.

Minimal local state:
  terminal checkpoint + bounded post-terminal retention allowed.

Strict local state:
  retain active task breadcrumb only while task is nonterminal;
  after terminal checkpoint, remove task and omit recent-signal retention.

Passive-only:
  no integration breadcrumb is created.
```

**Required edits:**

1. Add privacy-profile precedence to `01` and `03`.
2. Add Strict-mode branches to `14` breadcrumb checkpoint and terminal retention rules.
3. Update `22` recovery/Safe Mode wording so recovery never resurrects a strict-mode terminal breadcrumb.
4. Add retention fixtures for Minimal vs Strict vs Passive-only.

### R-08 · Safe Mode is conceptually correct but not operationally closed

**Severity:** P0  
**Documents:** `08-integration-hook-protocol.md`, `14-spike-c-link-transport-drop-mode.md`, `20-onboarding-settings-and-capability-disclosure.md`, `21-install-update-uninstall-contract.md`, `22-reliability-recovery-and-diagnostics.md`

`22` says Safe Mode disables Pulse Hook integrations “for Pulse use,” does not remove provider Hook entries automatically, and does not launch Link. Existing provider Hook entries can still invoke `pulse-link-shim.exe`, so the exact no-op point needs to be specified.

**Decision to lock:**

```text
Safe Mode is enforced at the earliest Pulse-owned executable boundary.

Shim sees a current-user Safe Mode flag
→ does no Link wake or event forwarding
→ exits 0 within normal fail-open budget.

Existing provider Hook configuration remains untouched.
Island does not request Link wake while Safe Mode is active.
User can explicitly re-enable observation or remove integrations.
```

**Required edits:**

1. Add Safe Mode behavior to `08` Shim rules and `14` startup scenarios.
2. Add Safe Mode state to onboarding/integration cards in `20`.
3. Add Safe Mode to update/repair/uninstall edge cases in `21`.
4. Add a measured Safe Mode acceptance scenario: existing Hooks invoke Shim, Link is not spawned, provider execution is unchanged.

## 3. P1 closure items

These do not invalidate the core architecture, but should be corrected before provider adapter work begins.

### R-09 · Safe task-title source is too permissive in the privacy baseline

**Documents:** `01`, `02`, `07`, `16`, `17`, `20`

`01` permits deriving a title from an allow-listed first user-intent field. The Codex and Claude probe cards deliberately prohibit retaining prompt text and do not establish a P0 safe task-title source. This can tempt an adapter to convert a user prompt into a label.

**Correction:** Safe title is unavailable by default. It may appear only from a provider field explicitly classified safe in that provider’s probe card and release matrix. Otherwise use a generic provider/workspace label.

---

### R-10 · Integration ownership identification must not rely on unsupported config keys

**Documents:** `01`, `08`, `16`, `17`, `21`

`08` uses conceptual `owner` / `integration_id` metadata examples. `16` and `17` correctly say provider schemas may reject arbitrary metadata and identify Pulse entries by an exact executable-plus-arguments signature.

**Correction:** The cross-provider contract should say “provider-compatible Pulse-owned command signature plus non-secret installation ID.” Provider-specific schemas decide where that signature is represented. Never add unknown metadata fields only to make Pulse’s uninstall easier.

---

### R-11 · Release labels, task health, and route capabilities are three different axes

**Documents:** `02`, `07`, `15`, `19`, `20`

The package sometimes uses `workspace_ready` as a release label, while elsewhere it is a task context capability. It also mixes provider release labels (`supported_observe`) with runtime health (`attached`, `degraded`) in prose.

**Correction:** Add a one-page taxonomy table:

| Axis | Examples |
|---|---|
| Provider release status | `not_probed`, `process_observed`, `experimental_attached`, `supported_observe`, `supported_fuel` |
| Per-task health | `attached`, `observed`, `degraded`, `offline` |
| Per-task route capability | `none`, `agent_ready`, `workspace_ready`, `context_ready` |
| Per-task feature capability | `observe_waiting`, `open_workspace`, `observe_quota_snapshot` |

`workspace_ready` must not be presented as a provider release label.

---

### R-12 · Generic local structured-state support must remain source-gated

**Documents:** `03`, `06`, `07`, `15`, `16`, `17`, `19`

The platform architecture allows formally validated local structured-state readers. The Codex and Claude cards currently reject raw transcript/session-file parsing as a P0 source. This is compatible, but the generic wording in `06` could be read as permission to implement a file scanner for initial adapters.

**Correction:** In `06` and `07`, state that structured-local-state mode is framework capability only. It is disabled for a provider unless its probe card and capability report name an approved schema and allow-list.

---

### R-13 · Review fixtures need a few cross-layer scenarios

**Documents:** `12`, `13`, `14`, `22`, `24`

The test package is already strong. Add these scenarios so the corrected contracts cannot drift again:

1. `failed + waiting + limited` tier ordering.
2. Strong window route must not use exact-route wording.
3. Strict profile removes terminal breadcrumb at terminal transition.
4. Safe Mode keeps existing provider Hooks fail-open but prevents Link spawn.
5. Island reconnect receives full snapshot/delta only, never event batch/replay.
6. Process-only Antigravity cannot render a running or terminal task state.
7. Fuel source availability differs by provider and can be revoked without changing lifecycle truth.

## 8. Final conclusion

The package does **not** have an architectural hole in its core idea. It has a healthy core and a handful of “older overview versus newer probe contract” mismatches. The most important correction is conceptual:

> Provider capability, Fuel capability, route certainty, and task state are independent axes.

Once the package encodes that rule consistently, Pulse Island has a clean implementation path: first make truth deterministic, then make the desktop signal elegant, then make Link tiny and fail-open, then let real providers earn their claims one capability at a time.
